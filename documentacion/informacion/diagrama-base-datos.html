Catálogo de tablas y campos

Abre una ficha para ver los campos relevantes, su función y las reglas de relación. Busca por nombre o campo para filtrar.

roles · catálogo de perfiles

Define los perfiles de acceso usados por las cuentas.

  • id (PK), name único, description opcional y marcas de tiempo.
  • Relación: un rol puede asociarse a varias cuentas mediante usuarios.role_id (FK).
usuarios · cuentas del sistema

Datos de autenticación y rol.

  • id (PK), username único, nombre, apellidos, email opcional y único, contraseña cifrada, role_id (FK), activo, remember token y timestamps.
  • Sanctum admite tokens polimórficos en personal_access_tokens; la app Android actual, sin embargo, utiliza el portal web y sesión.
pacientes · expediente

Guarda los datos del paciente y antecedentes registrados.

  • id (PK), user_id opcional, nombre, apellidos, teléfono, email, fecha de nacimiento, alergias, enfermedades, tratamientos y timestamps.
  • user_id no tiene FK ni índice en la migración. Existe una asociación Eloquent con usuarios.
  • Un paciente puede tener muchas citas y casos clínicos; ambas relaciones sí están respaldadas por FK.
servicios · catálogo de servicios

Nombre, descripción opcional, precio decimal y timestamps. Una cita puede referenciar un servicio; en la estructura actual citas.servicio_id es opcional. Al borrar un servicio, la FK de la migración inicial indica borrado en cascada de sus citas.

solicitudes_citas · peticiones públicas

Conserva datos de contacto, propuesta de fecha/hora, motivo opcional, nacimiento, estado y timestamps. Estados de BD: esperando_confirmacion, cancelada, confirmada. No tiene FK a la cuenta, al expediente ni a la cita que se crea al aprobarla.

citas · agenda y resultado de atención

id (PK), paciente_id obligatorio (FK), caso_clinico_id opcional (FK), servicio_id opcional (FK), tratamiento realizado opcional, fecha, hora, estado, origen, marca temporal del recordatorio y timestamps. Estados: en espera, confirmada, realizada, cancelada y no se presentó. No hay restricción única de fecha/hora para todas las citas.

Al borrar el paciente, las citas se eliminan por cascada; al borrar el caso, se conserva la cita y se limpia su referencia. El precio vigente del servicio no se copia como precio histórico.

casos_clinicos · seguimiento de tratamientos

id (PK), paciente_id obligatorio (FK con cascada), tratamiento base, progreso, estado y timestamps. La migración de BD limita el estado a activo o finalizado; el modelo también declara suspendido. No guardar estados adicionales sin alinear primero la migración.

horarios_bloqueados · bloqueos de agenda

Fecha, hora, motivo, usuario responsable opcional (FK a usuarios con SET NULL) y timestamps. Una restricción única evita duplicar la misma fecha y hora en esta tabla.

ofertas · contenido promocional

Título, tag opcional, descripción, precio opcional, orden, indicador activo y timestamps. No tiene relaciones con otras tablas.

office_settings · datos del consultorio

Nombre, dirección, URL de mapa y teléfono de WhatsApp, con timestamps. La migración agrega inicialmente la fila id 1, pero no impone que la tabla contenga una sola fila.

password_reset_tokens · recuperación

Email indexado, token y fecha de creación. La migración no declara PK ni FK a usuarios; la gestiona Laravel Password Broker.

personal_access_tokens · tokens Sanctum

Clave polimórfica tokenable_type/tokenable_id, nombre, token único, permisos, fechas de uso/expiración y timestamps. Tiene índice polimórfico, no una FK directa a usuarios. Es infraestructura disponible para API, no el mecanismo de sesión usado por la app Android actual.

push_devices · dispositivos push

Usuario (FK con borrado en cascada), token único, plataforma y timestamps. La tabla y endpoints existen; el cliente Android actual no registra el dispositivo, por lo que no se debe asumir que push esté activo.

cache · almacenamiento auxiliar

Clave primaria key, valor y expiración indexada. Tabla técnica de Laravel si el driver de caché usa la base de datos.

cache_locks · bloqueos de caché

Clave primaria key, propietario del bloqueo y expiración indexada. Tabla técnica de Laravel; no contiene relaciones clínicas.

Nota para interpretar el diagrama: una FK garantiza una referencia según la base de datos y su regla al borrar. Una relación de Eloquent solo describe cómo consulta Laravel. Las solicitudes no se convierten en cita mediante una FK: al confirmarlas, el controlador crea el expediente y la cita en una transacción. Compara estas migraciones con la base del hosting antes de hacer cambios.
