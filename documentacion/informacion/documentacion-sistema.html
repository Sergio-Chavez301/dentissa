Arquitectura

Backend

Laravel 12, PHP 8.2+, rutas web, controladores, middleware, Eloquent y plantillas Blade.

Interfaz

Blade, Bootstrap 5, Bootstrap Icons y CSS/JavaScript procesados con Vite, Tailwind 4 y Bootstrap npm.

Datos

MySQL/MariaDB en el entorno actual; migraciones portables y datos operativos en base relacional.

La entrada web es public/index.php. Configura el document root del hosting en public/, no en la raíz del repositorio. La web pública muestra inicio, solicitudes, ofertas, mapa y WhatsApp; las áreas privadas usan sesión autenticada.

Módulos

Autenticación y recuperación

Inicio y cierre de sesión, perfil, solicitud de restablecimiento y cambio por token de Laravel Password Broker. La ruta de solicitud limita tráfico a 3 intentos por minuto y entrega respuesta genérica para no enumerar correos.

Pacientes y cuentas

El personal registra expediente; al crear una cuenta de paciente se asigna role_id 3. La gestión de usuario/contraseña temporal de pacientes está limitada al administrador. El asistente no puede acceder a esas rutas.

Solicitudes y agenda

El formulario público crea solicitudes, no citas inmediatas. Al confirmar se vuelve a validar disponibilidad, se crea cuenta y paciente y se inserta una cita confirmada; el rechazo cancela la solicitud. Las citas manuales nuevas empiezan en espera.

Casos y seguimiento

Un caso corresponde a un expediente y puede tener citas asociadas; cada cita puede opcionalmente pertenecer a un caso. El panel del paciente muestra progreso y citas realizadas asociadas.

Contenido y consultorio

Ofertas activas se muestran en web pública y panel de paciente. La fila de office_settings guarda nombre, dirección, URL de mapa y WhatsApp; el administrador puede editarla y el frontend deriva mapa incrustado desde la dirección.

Reportes

Resumen de citas, pacientes, casos, servicios e importes estimados; los estados mostrados deben mantenerse en sincronía con el enum de citas.

Modelo de datos

Consulta el diagrama interactivo para campos y relaciones. Las tablas centrales son roles, usuarios, pacientes, servicios, solicitudes_citas, citas, casos_clinicos, horarios_bloqueados, ofertas, office_settings y password_reset_tokens.

Las FK reales se declaran en migraciones: usuarios→roles, citas→pacientes/servicios/casos, casos→pacientes y bloqueos→usuarios. pacientes.user_id se usa como relación Eloquent pero no tiene FK declarada. Solicitud, ofertas, settings y tokens son tablas independientes.

Configuración

Variables de entorno de referencia

.env.example no contiene secretos. Define APP_KEY, APP_URL y credenciales MySQL en el panel privado del hosting, nunca en GitHub. En producción usa APP_ENV=production, APP_DEBUG=false y HTTPS.

La plantilla recomienda SESSION_DRIVER=file, CACHE_STORE=file y QUEUE_CONNECTION=sync porque el repositorio no incluye migraciones para tablas de sesiones/caché/jobs.

Correo de recuperación

MAIL_MAILER=log no envía correo real. Usa proveedor transaccional SMTP y dominio verificado (SPF/DKIM/DMARC); el controlador bloquea reset en producción si se mantiene `log`, para no exponer enlaces en logs.

Almacenamiento

Los archivos privados usan storage local. Si se agregan imágenes clínicas, valida privacidad, backups y permisos; no publiques documentos sensibles mediante el disco public.

Despliegue en hosting conectado a GitHub

  1. El hosting debe ejecutar Laravel/PHP; GitHub Pages no sirve PHP.
  2. Usa PHP 8.2+, Composer y extensiones requeridas, en especial pdo_mysql, mbstring, openssl, fileinfo, xml, ctype y json.
  3. Clona el repositorio, instala dependencias de producción y ejecuta npm ci && npm run build (o sube artefactos compilados según el proveedor).
  4. Configura document root a public/, crea base MySQL y define variables privadas.
  5. Ejecuta php artisan key:generate solo en la instancia nueva y luego php artisan migrate --force.
  6. Permite escritura en storage/ y bootstrap/cache/; ejecuta storage:link si el proyecto expone archivos públicos.
  7. Activa HTTPS, APP_DEBUG=false, SMTP, caché de configuración y una estrategia de backup antes de recibir datos reales.

Hallazgos a revisar

Esquema

Estados de caso clínico: la migración permite activo y finalizado; el update acepta también pausado y completado; el modelo declara suspendido. Alinear antes de usar todos los estados en MySQL estricto.

Relación

Vínculo usuario-paciente: pacientes.user_id no tiene FK ni índice en la migración. Asegurar que la aplicación crea vínculos y decidir si se añade constraint con limpieza de datos planificada.

Autorización

La auditoría de rutas/controladores encontró CRUDs donde el control de rol depende de que el usuario no sea paciente, o no aparece en controlador. Revisa especialmente recursos de casos, servicios, dashboards y solicitudes antes de operar con datos sensibles. Ocultar botones no es autorización.

Agenda

La disponibilidad se comprueba en aplicación, pero no existe índice único de citas sobre fecha/hora. Dos solicitudes concurrentes podrían competir por el mismo bloque; evaluar bloqueo transaccional o reserva atómica.

Verificado en fuente

La documentación describe el estado del repositorio y no sustituye revisar la base real del servidor. Los tests feature del entorno local requieren pdo_sqlite; su ausencia impide ejecutar las pruebas con phpunit.xml actual.
