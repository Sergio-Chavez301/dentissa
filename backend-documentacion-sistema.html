Backend

Documentación técnica del sistema Dentissa

Esta guía está pensada para colaboradores que van a hacer upgrades o mantenimiento. Explica el comportamiento backend del sistema, la relación entre entidades, los controladores y las reglas de negocio.

Framework

Laravel 12 con PHP 8.2, Blade, Eloquent ORM y rutas protegidas por middleware.

Base de datos

MySQL con tablas principales: roles, usuarios, pacientes, servicios, citas, casos_clinicos, solicitudes_citas y ofertas.

Autenticación

Se maneja con Laravel Auth + login por username y password. Los roles se diferencian por role_id.

1. Objetivo del sistema

Dentissa es un sistema de gestión odontológica con estas funcionalidades principales:

  • Gestión de usuarios y roles.
  • Registro y seguimiento de pacientes.
  • Agendamiento de citas.
  • Administración de casos clínicos.
  • Solicitudes de cita desde la web pública.
  • Contenido web promocional (ofertas).
  • Reportes y dashboards por rol.

2. Roles y permisos

Rol ID Permisos clave
Administrador 1 Usuarios, pacientes, citas, servicios, solicitudes, reportes, contenido web
Asistente 2 Pacientes, citas, casos y agenda
Paciente 3 Ver su expediente, citas y casos
El login usa el campo username, no email. El role_id determina por qué dashboard entra cada usuario.

3. Estructura de entidades

Modelo User

  • username
  • nombre
  • apellidos
  • email
  • password
  • role_id
  • activo

Modelo Patient

  • nombre, apellidos
  • email
  • telefono
  • fecha_nacimiento
  • alergias, enfermedades, tratamientos
  • user_id

Modelo Cita

  • paciente_id
  • servicio_id
  • fecha
  • hora
  • estado

Modelo CasoClinico

  • paciente_id
  • tratamiento_base
  • progreso
  • estado

4. Relación entre entidades

User (1) ── belongsTo ── Role User (1) ── hasOne ── Patient Patient (1) ── hasMany ── Cita Patient (1) ── hasMany ── CasoClinico Cita (many) ── belongsTo ── Servicio CasoClinico (many) ── belongsTo ── Patient SolicitudCita ── se convierte en Patient + Cita cuando se confirma
La clave importante es que el paciente puede tener un usuario de acceso, pero la cita y el caso clínico siempre apuntan al paciente, no directamente al usuario.

5. Controladores principales

Controlador Responsabilidad
AuthController Login, logout, recuperación de contraseña.
PatientController CRUD de pacientes, creación de usuario asociado y dashboard del paciente.
CitaController Agenda, disponibilidad, edición, cambio de estado.
SolicitudController Formulario público, confirmación y rechazo de solicitudes de cita.
CasoClinicoController Registro, actualización y consulta de casos.
OfertaController Gestión de contenido promocional para la home pública.

6. Reglas de negocio clave

  1. Rol paciente: si un usuario entra con role_id = 3, se redirige al dashboard del paciente.
  2. Usuario paciente no opcional: si un paciente es creado desde una cita o caso, el sistema crea su acceso web de forma automática.
  3. Citas no duplicadas: la hora se valida con disponibilidad real.
  4. Solicitudes públicas: no crean cita aún; se convierten a cita únicamente si el admin confirma.
  5. Casos clínicos: cada caso debe corresponder a un paciente y mostrar progreso entre 0 y 100.
  6. Credenciales temporales: la contraseña temporal solo sirve para primer ingreso; luego debe ser cambiada.

7. Flujo real del backend

1. Usuario visita /login 2. AuthController::login() valida username + password + activo 3. Si es paciente, redirige a dashboard.paciente 4. Admin crea paciente o cita o caso clínico 5. En algunos casos, PatientController crea automáticamente el User 6. En citas con paciente nuevo, CitaController crea User + Patient + Cita 7. En solicitud pública confirmada, SolicitudController crea User + Patient + Cita 8. En caso clínico, CasoClinicoController crea o asocia el paciente y el caso 9. La app renderiza la vista con la información del paciente y su historial

8. Consideraciones para futuros upgrades

  • No mezclar la lógica de acceso con la lógica de negocio del paciente.
  • Guardar todas las transformaciones en servicios si se vuelven más complejas.
  • Centralizar validaciones de disponibilidad de citas en un servicio reutilizable.
  • Mantener separadas las tablas de usuarios, pacientes y citas para un mejor mantenimiento.
  • Los cambios de estado deben ir por validación y no por lógica no controlada.

9. Punto de extensión recomendado

Si se añaden nuevas funcionalidades, lo mejor es crear servicios como:

  • PacienteService
  • CitaService
  • SolicitudService
  • ReporteService

Así se separa la lógica del controlador y se facilita la colaboración entre equipos.
